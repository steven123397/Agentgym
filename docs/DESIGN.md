# 专注任务规划器 · 设计文档

## 1. 目标与范围

在现有零依赖前端基座上实现「专注任务规划器」：用户维护一组任务（标题、优先级、预计耗时、截止时间、完成状态），应用根据确定性算法为「今天」生成一份不超过 8 小时（480 分钟）的执行计划，并在数据为空时提供独立的初始落地页。

范围：纯前端、localStorage 持久化、无后端、无数据库、无新增第三方依赖。

## 2. 页面结构与主要交互

### 2.1 视图状态机

应用只有两种顶层视图：**初始页** 与 **工作台**。切换规则完全由数据与一个内存标志决定：

- `任务数为 0 且 未主动进入工作台` → 初始页
- 其他情况 → 工作台
- 删除最后一个任务后，内存标志重置，自动回到初始页（满足「任务被全部删除后回到初始页或等价引导态」）

状态只存内存；刷新后仅任务数据从 localStorage 恢复（任务数 > 0 时进入工作台，任务数为 0 时回到初始页）。

### 2.2 初始页（落地页）

- 顶部 Hero：产品价值主张（一句话标题 + 副标题）、主操作按钮「创建第一个任务」、次操作「直接进入工作台」（进入带空状态引导的工作台）。
- 中部能力说明：三张卡片介绍「任务管理」「智能排序」「8 小时预算」，用轻量 CSS 装饰（渐变、卡片、图标字符）体现视觉层次。
- 底部无额外内容；整个页面在 360px 宽度下仍可读、按钮可点。
- 从初始页的「创建第一个任务」直接打开新增任务对话框，保存成功后进入工作台。

### 2.3 工作台

- 顶栏：品牌名、视图切换（全部任务 / 今日计划）、「新增任务」按钮。
- **全部任务视图**：任务卡片列表。每张卡片含完成复选框、标题、优先级徽章、预计耗时、截止时间（含逾期标记）、编辑与删除按钮。列表排序：未完成在前、已完成在后；组内按优先级（高→中→低）、截止时间、创建时间排序。
- **今日计划视图**：自动生成并展示计划（进入视图即重新计算，无需手动按钮）：
  - 摘要条：已安排用时 / 480 分钟，附「已完成任务不参与今日计划」说明；
  - 计划时间轴：按执行顺序展示任务及其计划开始/结束时间（默认从 09:00 开始，逐项累加）；
  - 「无法安排的任务」区块：逐条显示原因。
- 计划视图中的任务同样提供完成复选框，勾选后实时重算计划。

### 2.4 新增 / 编辑对话框

- 使用原生 `<dialog>` 模态框，含 5 个字段：标题、优先级（低/中/高）、预计耗时（分钟）、截止时间（datetime-local）、已完成（新增时默认未完成，编辑时回填）。
- 保存时校验：标题去空格后非空且 ≤ 80 字符；预计耗时为 1–1440 的整数；截止时间为有效日期。错误以内联文本提示，不阻塞对话框关闭前的其他操作。
- 删除使用行内二次确认（按钮变为「确认删除」，3 秒未确认自动还原），不使用阻塞式 `confirm()`。

### 2.5 空状态与错误状态

- 工作台无任务（从初始页「进入工作台」进入）：展示引导空状态，含「创建第一个任务」按钮。
- 计划视图无未完成任务：提示「没有待办任务」；有任务但没有可安排项时展示对应原因。
- localStorage 读取损坏（非法 JSON / 字段不合法）：安全降级为空列表并在控制台告警，不崩溃。
- 用户输入一律 HTML 转义后渲染，防止 XSS。

## 3. 核心数据模型

```ts
interface Task {
  id: string;                 // 唯一 ID（crypto.randomUUID，或兜底随机串）
  title: string;              // 1–80 字符
  priority: "high" | "medium" | "low";
  estimateMinutes: number;    // 1–1440 的正整数
  dueAt: number;              // 截止时间，epoch 毫秒数
  completed: boolean;
  createdAt: number;          // 创建时间，epoch 毫秒数，用于稳定排序
}
```

`dueAt` 存 epoch 毫秒而不是本地字符串，避免 `datetime-local` 与排序/比较之间的时区解析歧义；显示时再格式化为本地时间。

## 5. 任务计划生成算法

### 5.1 输入与输出

```ts
buildTodayPlan(tasks, { now = Date.now(), budgetMinutes = 480 })
// -> { scheduled: Array<{ task, startMinutes, endMinutes }>,
//      excluded:  Array<{ task, reason: "budget", neededMinutes, remainingMinutes }>,
//      usedMinutes, budgetMinutes }
```

`startMinutes`/`endMinutes` 是相对工作日起始时刻的偏移量（工作日起始 = 09:00，即 540 分钟处），供 UI 换算时钟时间。

### 5.2 步骤

1. **候选集**：所有 `completed === false` 的任务（已完成任务完全不参与计划）。
2. **确定性排序**，按以下键依次比较：
   1. 优先级降序（high=3 > medium=2 > low=1）—— 高优先级优先；
   2. `dueAt` 升序（截止时间更近优先；逾期任务自然排最前）—— 截止时间近优先；
   3. `createdAt` 升序 —— 更早创建的先排；
   4. `id` 升序 —— 兜底，保证任何输入都完全确定。
3. **贪心放入**：`remaining = budgetMinutes`；依序遍历候选：
   - 若 `estimateMinutes <= remaining`：放入 `scheduled`（记录起止偏移），`remaining -= estimateMinutes`；
   - 否则：放入 `excluded`，记录 `reason: "budget"`、`neededMinutes` 与当前 `remainingMinutes`，继续检查后续任务（不跳过剩余候选）。
4. 返回结果。

### 5.3 未安排原因

`excluded` 中的任务由 UI 按原因渲染：

- `remainingMinutes === 0`：「今日 8 小时预算已用完」；
- `0 < remainingMinutes < neededMinutes`：「今日剩余 X 分钟，不足以完成（预计 Y 分钟）」。

### 5.4 算法性质

- 确定：同一输入、同一 `now` 与预算，输出逐位相同。
- 顺序忠实：贪心不越序，绝不跳过更紧急的任务去凑时间，因此可能不是「最优装箱」，但语义可解释。
- 完整性：放不下的任务绝不半安排，并给出明确原因。

## 6. 关键边界情况

- 无任务或全部已完成 → 空计划（`scheduled`、`excluded` 均为空）。
- 单个任务预计耗时超过 480 分钟 → 排除并显示预算原因。
- 恰好用满 480 分钟 → 全部放入，`remaining === 0`。
- 同优先级比截止时间；截止时间相同比创建时间；全部相同比 id。
- 逾期任务参与计划并排在同优先级的最前。
- 中途某任务放不下 → 跳过它，后续更小的任务仍可放入（顺序忠实）。
- localStorage 缺失 / JSON 损坏 / 字段非法 → 空列表或剔除非法项，控制台告警。
- 标题含 `<`、`&` 等字符 → 转义后渲染。
- 移动端（≥320px）布局可用：卡片单列、按钮不溢出。

## 7. localStorage 数据结构

单键存储，版本号内嵌在键名中，便于将来迁移：

```json
{
  "key": "focus-planner:tasks:v1",
  "value": "[{\"id\":\"a1b2\",\"title\":\"写周报\",\"priority\":\"high\",\"estimateMinutes\":45,\"dueAt\":1754035200000,\"completed\":false,\"createdAt\":1754031000000}]"
}
```

读取流程：取原始字符串 → 解析 JSON → 逐项 `normalizeTask`（校验字段类型与范围，非法项剔除）→ 返回数组。写入流程：整数组 `JSON.stringify` 后 `setItem`；异常时捕获并控制台告警（内存数据仍可用）。

## 8. 测试和验证方案

### 8.1 自动化测试（`npm test`，Node 内置测试运行器）

- `tests/baseline.test.js`：保持不动，继续验证挂载点与入口脚本。
- `tests/planner.test.js`：排序规则（优先级、截止时间、逾期、稳定兜底）；预算上限与恰好用满；放不下任务的跳过与原因；已完成任务排除；确定性（同输入同输出）。
- `tests/store.test.js`：空存储、往返读写、损坏 JSON 降级、非法字段剔除、键名版本。
- `tests/format.test.js`：HTML 转义、分钟数格式化、datetime-local 值转换、逾期标记。

### 8.2 手工/启动验证

1. `npm run dev` 启动，访问 `http://127.0.0.1:4173`；
2. 检查初始页：价值主张、双入口、移动端宽度可读；
3. 走通主流程：新增（含校验错误）→ 列表展示 → 编辑 → 标记完成/取消 → 删除（含二次确认）→ 全部删除后回到初始页；
4. 今日计划视图：排序、8 小时预算、无法安排原因、勾选完成实时重算；
5. 刷新页面确认数据保留（localStorage）；
6. 缩小到移动端宽度检查布局。

## 9. 实现中的主要取舍

- **今日计划候选 = 全部未完成任务**（而非仅今日到期）：保证计划视图在任何数据下都可解释、可用；逾期与今日到期任务因排序自然置顶。
- **贪心顺序算法而非背包最优**：牺牲「塞得更满」，换取优先级语义不被破坏、行为确定且容易向用户解释。
- **`dueAt` 用 epoch 毫秒存储**：避免 `datetime-local` 字符串在比较与跨时区展示上的歧义。
- **无路由、无框架、无构建**：视图由状态渲染，刷新后只恢复数据（默认视图合理即可），符合基座的技术约束。
- **删除用行内二次确认**：避免阻塞式 `confirm()` 在不同浏览器/嵌入环境下的行为差异。
- **计划默认从 09:00 起算**：固定常量，方便展示时间轴；不做个性化工作时段设置（超出任务范围）。

## 10. 明确不做的事

- 不做后端、账号、数据库、远程服务。
- 不做拖拽排序、重复任务、子任务、提醒通知。
- 不做按项目/标签分类与搜索（任务字段与需求未包含）。
- 不重写 `index.html`、`scripts/dev-server.mjs` 等与业务无关的基座文件。
